  - 64 条为 0 条 evidence。
  - 其中 4 条已有 `sourceKey/conversationKey/displayName`，但 evidence 为空；60 条历史记录缺少自动化联系人桥接字段。
- 51 平台读取聊天上下文时还有一个上游限制：
  - `job51_read_chat_context()` 直接调用 `job51_extract_chat_messages()`。
  - `job51_extract_chat_messages()` 只抓当前 DOM 中已经渲染出来的 `div.message-item.mine` 和 `div.message-item.others`。
  - 目前没有在读取前滚动聊天消息面板向上加载历史消息，所以如果 51 页面只渲染当前可见/最近消息，老消息不会进入 memory。

- 如果看到的是简历库联系人元数据里的聊天证据，短是当前设计导致的：该字段只保留 3 条，并且大量 51 历史简历还没有桥接出 evidence。

- 将 51 的聊天读取增加“消息面板向上加载历史”步骤：打开候选人后先对聊天消息容器向上滚动有限次数，直到消息数量不再增加，再提取 DOM 消息，最后恢复到底部继续处理。
- 调整简历联系人桥接回填条件：即使已有 `displayName/conversationKey`，只要 `platformContact.chatEvidence` 为空，也应尝试从 memory 或 batch report 补齐 evidence。
- 前端文案上区分“联系人证据”和“完整聊天记录”，避免把最多 3 条的 `chatEvidence` 误认为完整聊天。

### 核心原因
- 24h 自动处理进度兜底重复计数：
  - 24h 日志里有一条 `target_completed`，当前状态快照里也有同一目标。
  - 原逻辑同时把日志进度和状态快照加入兜底，导致 `51 宋峰峰` 处理人数从 58 被叠成 116，获取简历从 40 被叠成 80。
